## 3. 需要优先处理的架构问题

### AR-05a 升级删除列破坏已测试 N-1 的页面写入路径

**P1，代码确认并在内存库复现。** `20260930_0100` 删除 `ai_page_mutation_batches.lease_generation`，但 M05 选择的 N-1 `4c7eee8` 仍在 `AiPageMutationBatch` ORM 中映射该列。旧版 `page_mutation_enqueue.py` 使用 `select(AiPageMutationBatch)` 查找 pending Batch，读取会选择包括该列在内的全部 ORM 字段。

本轮从 Git 读取实际旧模型，使用独立 DeclarativeBase 编译查询，在按当前模型列集合创建的空内存表执行，得到：

```text
no such column: ai_page_mutation_batches.lease_generation
```

即使没有历史 Batch 行，查询也会因缺列失败。M05 中两版登录均 200 的记录可以保留，但不能推出“旧应用在新 schema 上业务可运行”。这里既有新增列，也有删除列；“多余列可忽略”没有覆盖这次变化。

**建议：** 当前组合先按停机升级约束操作，禁止 N-1 页面写入流量在删列后继续运行。若要支持滚动和仅回退应用镜像，应跨发布保留旧列：先发布停止使用旧列的代码，确认旧实例退出和回滚窗口结束，再执行删除迁移。是否通过补偿迁移恢复列，应在实施时结合该 revision 的发布状态决定。

验收必须覆盖 N-1 在 N schema 上的页面任务入队、Batch 读取/写入、取消及外部续跑，不能只检查登录。依据：[删列迁移](../../../../backend/migrations/versions/20260930_0100_drop_page_mutation_batch_lease_generation.py)、[当前入队路径](../../../../backend/app/ai/page_mutation_enqueue.py)、[M05 记录](../runs/2026-09-30-a06120e/m05/summary.md)。旧代码可用 `git show 4c7eee8:backend/app/models/ai_page_mutation.py` 与相同 ref 下的入队文件核对。

### AR-05b 普通 Run 的跨容器遗留收敛没有生产闭环

**P1，静态确认。** 启动恢复按 hostname/PID 过滤，保护其他实例，这一方向正确。但容器重建改变 hostname 后，旧 Run 被跳过；`recover_stale_active_run()` 在生产源码中只有定义和说明文字，没有实际调用，调用只出现在集成测试。SSE 已明确忽略 idle timeout，保持纯观察；`get_active_run()` 也只是读取，`ensure_no_active_run()` 会拒绝有非终态 Run 的新请求。

因此，“旧 hostname Run 会由空闲超时自动终态化”目前没有实现依据。异常停止留下的 Run 可能持续占据会话，最终依赖用户取消。正常退出管理器能取消本进程任务，不覆盖进程被强杀的情况。

**建议：** 增加独立于 SSE 的 owner 存活登记与过期收敛路径，以持久化心跳、实例身份和 CAS 决定谁可以写终态；继续维持普通 Run 不自动续跑。不要直接按“多久没有模型事件”全局失败化 Run，长工具执行和慢模型可能仍然存活。若暂不实现后台收敛，应明确只提供手动解除，撤回自动有界恢复描述。

验收场景是强杀 A、重建为新 hostname/PID、保持 B 的长任务活跃，并确认旧 Run 在约定时间内终态且会话可重新发起。依据：[启动恢复](../../../../backend/app/ai/run_recovery.py)、[空闲方法与活跃检查](../../../../backend/app/ai/platform_runtime.py)、[SSE 观察链路](../../../../backend/app/ai/run_sse_stream.py)、[会话门面](../../../../backend/app/ai/session_facade_pydantic.py)。

### AR-05c 版本指纹没有覆盖正常浏览器预览的完整链路

**P1，静态确认。** 当前检查只在 `__preview` HTML 入口执行；无 `x-expected-runtime-version-fingerprint` 请求头时放行。全仓搜索未找到 Backend、Gateway 或 Editor 自动设置该期望值的生产代码，后续虚拟模块分支也没有调用该检查。Backend HTML 代理响应仅保留 Content-Type，不传出 Runtime 的指纹响应头。

还有两个配置问题：镜像没有固定注入发布构建标识，未配置时各版本可能都成为 `1.0.0+dev`；分角色模板把 `RUNTIME_BUILD_ID` 写成 `runtime-preview-1/2`，把发布身份和副本身份混在一起，同版副本反而不同指纹。

M05-F 已证明“人工携带失配头的入口请求返回 409”，没有证明正常 iframe 导航与模块请求可以阻止混版。页面源码公开路径 `.vN` 的兼容约束继续有效，但它不等价于 Runtime 编译器与壳层版本相同。

**建议：** 发布时注入同一源码/镜像构建标识，副本 ID 单独保存；由服务端创建预览时绑定版本，并把版本约束传播到 HTML、模块、CSS 和其他相关子请求，或采用明确的版本路由与整池切换。在此之前，同池只放同一发布版本，升级按排空/停机处理。

验收应真实打开浏览器，让 HTML 与至少一个模块落到不同版本，确认得到明确拒绝或稳定路由。依据：[指纹检查](../../../../runtime/src/core/plugins/runtime-health.ts)、[入口与模块分支](../../../../runtime/src/core/plugins/runtime-saas-preview.ts)、[Backend 代理](../../../../backend/app/api/routes/preview.py)、[模板](../../../../deploy/compose/compose.runtime-roles.yml)、[Runtime 镜像](../../../../runtime/Dockerfile)。

## 4. 容量结果与下一步执行策略

[混合负载](../runs/2026-09-30-a06120e/m03/summary.md) 记录 5 用户、并发 3、82 次操作、成功率 100%、合并 P95 97.96 秒、无 OOM、SQLite 写冲突与 busy timeout 均为 0。这证明该有限负载完成，不能推出 5–10 人持续并发的体验保证；机器使用 swap，且没有图片生成或独立交互预览的完整样本。

| ---: | ---: | ---: | ---: | ---: | ---: |

原摘要把高档位页更 0 次解释为编辑饥饿，还把截图数除以计划时长推导成固定服务时间。这些推论超过了原始数据：没有入队、开始、完成时间与独立请求到达记录，无法区分测试生成器被慢请求占住、阶段末尾在途任务与真实调度饥饿。`12/16` 档实际只完成截图，也不再代表同样的混合业务比例。单槽是 Lite 已设定的约束，不能据此标为 P0 故障；“预览并发 3”与“截图执行槽 1”也属于不同容量单位。

下一轮建议先补 `queue_wait_ms`、`execution_ms`、端到端时间、拒绝/超时、到达/完成数量和停止负载后的排空时间。独立发送预览、页更、截图和构建请求，分别统计；避免把成功结束的样本当全部到达请求。2C 上保持默认单槽，4C 上对比角色拆分与第二个单槽 Renderer，再决定是否提高全局预算。Renderer 继续保持单槽契约，多槽不是本轮推荐实现。

M03-F1 仍为待定位问题。当前内存后端会检查 String 的 key+value、Hash 的单 field+value 和总量，不能仅凭“总量 6.9 MB 小于 128 MiB”排除单项超限。但 drill 的 small/medium/large 循环实际反复创建同一整项目预览，既不是三种独立大小，也不是重复刷新同一个 artifact。先取得拒绝操作、实际 UTF-8 大小、命中的预算及清扫状态，再决定修实现还是修测试；不要先提高上限。依据：[内存预算](../../../../backend/app/services/runtime_state/memory_backend.py)、[运行态错误映射](../../../../backend/app/services/runtime_artifact_store.py)、[drill](../../../../scripts/testing/lite-runtime-state-drill.py)。

## 5. 应保留的边界与剩余维护成本

Backend 保持模块化控制面；Runtime 保持编译/预览角色；Renderer 保持每 attempt 浏览器执行；`render-contracts` 保持纯协议。共享 CAS、租约和写围栏继续承载可靠性，领域 Job、模型 step 的 Batch 与资源占用 Attempt 保持各自职责。当前进展没有给出引入微服务拆库或通用工作流平台的必要性。

W01 的 UID 与 0400 已保护全局 Worker 凭证，但所有执行子进程仍共用 UID/GID 10001，任务目录以同组可写权限创建。这不是任务之间的文件隔离证明；权限说明中的“只能访问自己的任务”需要更细的实测与实现边界。本轮没有证明用户 SFC 可执行任意 Node 代码，也没有进行逃逸实验。M02 应据既有威胁模型完成负例，不自动扩大成多租户隔离承诺。

大模块仍有维护成本，优先随高风险修改拆分，而不是再做全仓重排。当前物理行数含空行/注释、排除生成物：`runtime-build-runner.ts` 1684、`runtime-build-worker.ts` 1593、`runtime-saas-preview.ts` 1533、`asset_service.py` 1511、`project_template_package_service.py` 1861、`platform_runtime.py` 1236。下一次优先按凭证/身份、进程生命周期、工作区物化、产物上传拆 Runtime；包服务按解析、边界校验、导入事务与导出分责。分层白名单继续缩小，不以机械行数达标作为验收。
